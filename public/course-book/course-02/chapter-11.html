C02-CH11 — CRM REST API Foundations

  1. Chapter Orientation

1.1 Why this chapter matters Nova Field Service stores operational work in Zoho Creator, but CRM remains the source of truth for customer identity and service information. That boundary creates a practical integration requirement: Creator must be able to locate, read, create, update and relate CRM records without depending on display labels, browser clicks or undocumented assumptions. The CRM REST API provides HTTP endpoints for these operations. A reliable integration must also understand:

  • The API version in the request path.
  • The regional API domain.
  • Module and field API names.
  • OAuth scopes and user permissions.
  • Request and response envelopes.
  • Pagination.
  • API credits.
  • Concurrent request limits.
  • Error codes and retry decisions.
  • CRM record IDs versus Nova business IDs.

This chapter builds a small, testable CRM API collection and a mapping specification for Nova. The examples use Zoho CRM API V8 documentation and a .com API-domain assumption. No request in this chapter was executed against a live organization. 1.2 Learning outcomes By the end of this chapter, you should be able to: 1. Explain the structure of a Zoho CRM REST API URL. 2. Select a regional API domain and state the environment assumption. 3. Distinguish CRM display labels from module and field API names. 4. Retrieve module, field and related-list metadata. 5. Read one record and retrieve a page of records. 6. Search for a customer using an email or criteria query. 7. Create, update and delete records with the documented request envelopes. 8. Retrieve related records and list attachments. 9. Explain page limits, page tokens, credits and concurrency.

  1. Classify an API failure as configuration, data, permission, conflict, limit or transient failure.
  2. Build a CRM API collection that can be tested safely in a sandbox.
  3. Write a mapping specification that preserves Nova ownership and idempotency rules.

1.3 Prerequisites You should already understand:

  • Nova’s CRM-versus-Creator ownership boundary.
  • Creator forms, reports and Deluge data operations.
  • External calls using invokeurl.
  • External keys and idempotent integration design.
  • The distinction between a Creator record ID and a business key.

  1. Customer matching happens before a write.
  2. A duplicate or ambiguous match is not silently converted into a new customer.
  3. Creator records the outcome and remains able to reconcile the request later.

2.4 CRM API calls are side effects A CRM call can:

  • Consume API credits.
  • Trigger workflows unless explicitly controlled.
  • Create a new CRM record.
  • Modify customer data.
  • Return a record ID that must be stored.
  • Fail after a network timeout even though CRM may have completed the operation.

For that reason, a CRM call should be treated as a controlled side effect: validate → determine intended operation → resolve identity → call CRM → classify response → persist result → reconcile if outcome is uncertain Do not place a CRM write inside a loop without considering:

  • Maximum records per request.
  • Duplicate behavior.
  • Credit consumption.
  • Concurrency.
  • Partial success.
  • Retry safety.
  1. API Version, Domain and Request Shape

3.1 Verified API version The official Zoho CRM documentation pages used for this chapter are labeled V8. The examples therefore use: /crm/v8/ A production integration should verify the version required by the organization before release. Do not copy an older /crm/v2/ or /crm/v3/ URL into a V8 integration without checking the endpoint documentation. 3.2 API domain assumption Zoho CRM uses a region-specific API domain. The official examples accessed for this chapter use: https://www.zohoapis.com This chapter assumes a .com organization for examples: api_domain = https://www.zohoapis.com api_version = v8 A different organization may require another API domain. Keep the domain in an environment variable rather than embedding it in Deluge functions or multiple collection requests. The general URL shape is: {api-domain}/crm/{version}/{resource} Examples: https://www.zohoapis.com/crm/v8/settings/modules https://www.zohoapis.com/crm/v8/Contacts https://www.zohoapis.com/crm/v8/Contacts/{record_id} 3.3 Environment assumptions

EnvironmentAPI domainDataWrite policy
Development sandboxOrganization-specific sandbox domainSynthetic example.com contactsAllowed with a test key
UATOrganization-specific UAT domainApproved test fixturesAllowed with review
ProductionOrganization-specific production domainReal customer dataControlled and audited

The examples use synthetic values: Last_Name: Rivera Email: nova-api-test@example.com Phone: +1-555-010-0142 Do not use a real customer email in the collection. 3.4 Required headers A typical authenticated request includes: Authorization: Zoho-oauthtoken {{access_token}} For JSON write requests, also use: Content-Type: application/json For upload requests, use multipart form data. Do not manually set a multipart boundary unless the client requires it. Never commit an access token to:

  • A Git repository.
  • A Postman collection.
  • A screenshot.
  • A Creator source file.
  • A support ticket.

For multi-record writes, inspect every member of data.

  1. API Names and Metadata

4.1 Labels are for people; API names are for requests A CRM user may see a field label such as: Customer Email The API may require: Customer_Email__s The label can change without the API name changing. The reverse can also create confusion when a custom field has a label that is similar to a standard field. Use metadata to discover:

  • Module API name.
  • Field API name.
  • Field type.
  • Whether a field is readable.
  • Whether a field is writable.
  • Whether a field is searchable.
  • Whether a field is mandatory.
  • Picklist values.
  • Related-list API name.
  • Related-list href.

4.2 Module metadata Retrieve the available modules: GET {api-domain}/crm/v8/settings/modules Required scope: ZohoCRM.settings.modules.READ A documented module response contains values such as: { "modules": [ { "id": "5725767000000002179", "module_name": "Contacts", "plural_label": "Contacts", "singular_label": "Contact", "api_name": "Contacts", "api_supported": true, "viewable": true, "creatable": true, "editable": true, "deletable": true, "status": "visible" } ] } Use api_name in later URLs: Contacts Do not assume that a custom module’s label is its API name. 4.3 Field metadata Retrieve fields for a module: GET {api-domain}/crm/v8/settings/fields?module=Contacts Required scope: ZohoCRM.settings.fields.READ A useful field record may resemble: { "id": "5725767000000002599", "display_label": "Email", "field_label": "Email", "api_name": "Email", "data_type": "email", "json_type": "string", "read_only": false, "field_read_only": false, "system_mandatory": false, "searchable": true, "sortable": true, "operation_type": { "api_create": true, "api_update": true } } This example uses a standard Contacts field. A custom Nova field must be verified in the target organization. 4.4 Custom field names are organization-specific The following is an illustrative placeholder: Nova_Customer_Key__s It must not be treated as verified until the target CRM metadata returns that exact api_name. A safer mapping process is:

  1. Retrieve module metadata.
  2. Locate the desired module by api_name.
  3. Retrieve field metadata for that module.
  4. Match the intended field by label only as a discovery aid.
  5. Record the returned api_name.
  6. Check operation_type.api_create and operation_type.api_update.
  7. Check field type, length, searchability and uniqueness.
  8. Store the verified API name in configuration.

4.5 Related-list metadata Retrieve related lists for a module: GET {api-domain}/crm/v8/settings/related_lists?module=Contacts Required scope: ZohoCRM.settings.related_lists.READ Example response fragment: { "related_lists": [ { "display_label": "Notes", "api_name": "Notes", "href": "Contacts/{ENTITYID}/Notes", "status": "visible" }, { "display_label": "Attachments", "api_name": "Attachments", "href": "Contacts/{ENTITYID}/Attachments", "status": "visible" } ] } The href value is the source of truth for the related-record path. Do not infer a related-list path from a screen label. 4.6 Metadata retrieval order sequenceDiagram participant I as Integration participant M as CRM Metadata API participant R as CRM Records API

I->>M: GET /settings/modules M-->>I: module api_name I->>M: GET /settings/fields?module=Contacts M-->>I: field api_name and permissions I->>M: GET /settings/related_lists?module=Contacts M-->>I: related-list href I->>R: GET /Contacts?fields=... R-->>I: record data Metadata can be cached, but the cache needs an expiry or refresh process. An administrator can change a label, field permission, layout or related list after the integration is deployed.

  1. Read, Search and Paginate

5.1 Read one record To retrieve a specific Contact: GET {api-domain}/crm/v8/Contacts/{record_id} Example: curl --request GET \ --url "https://www.zohoapis.com/crm/v8/Contacts/5725767000001234567?fields=id,Last_Name,Email,Phone,Modified_Time" \ --header "Authorization: Zoho-oauthtoken ${ACCESS_TOKEN}" The record ID must be the CRM record ID, not NOV-CUST-001. 5.2 Read a page of records To retrieve a list of records, provide fields: GET {api-domain}/crm/v8/Contacts?fields=id,Last_Name,Email,Phone&page=1&per_page=50 The documented maximum per_page value for this endpoint is 200. A response may include: { "data": [ { "id": "5725767000001234567", "Last_Name": "Rivera", "Email": "nova-api-test@example.com", "Phone": "+1-555-010-0142" } ], "info": { "per_page": 50, "count": 1, "page": 1, "more_records": false } } For a list request, keep the field list narrow. A small field set:

  • Reduces response size.
  • Makes mapping clearer.
  • Reduces accidental exposure of sensitive fields.
  • Helps tests detect missing fields.

5.3 Search by email The Search Records endpoint supports email search: GET {api-domain}/crm/v8/Contacts/search?email=nova-api-test%40example.com Required scopes: ZohoCRM.modules.{module_name}.READ ZohoSearch.securesearch.READ Example: curl --get \ --url "https://www.zohoapis.com/crm/v8/Contacts/search" \ --data-urlencode "email=nova-api-test@example.com" \ --data-urlencode "fields=id,Last_Name,Email,Phone,Modified_Time" \ --header "Authorization: Zoho-oauthtoken ${ACCESS_TOKEN}" Email search checks the email fields in the specified module. 5.4 Search by criteria Criteria use the field API name: (field_API_name:operator:value) Example: (Email:equals:nova-api-test@example.com) A URL-encoded request can be created with a client rather than manually encoding punctuation: curl --get \ --url "https://www.zohoapis.com/crm/v8/Contacts/search" \ --data-urlencode "criteria=(Email:equals:nova-api-test@example.com)" \ --data-urlencode "fields=id,Last_Name,Email,Phone" \ --header "Authorization: Zoho-oauthtoken ${ACCESS_TOKEN}" The documented Search API behavior includes:

  • Maximum of 10 criteria.
  • criteria, email, phone and word search modes.
  • Only one mandatory search mode is processed at a time.
  • If several are supplied, the documented priority is criteria, email, phone, then word.
  • Search results can contain up to 2,000 records.
  • A single request returns at most 200 records.
  • Search immediately after a create or update can encounter indexing delay.

For a unique customer lookup, email matching is useful but should not be treated as proof of identity if the business permits duplicate emails. 5.5 Pagination with page numbers For up to the first 2,000 records: page=1&per_page=200 page=2&per_page=200 Continue while: "more_records": true A simple control rule is: page = 1 while more_records is true: request page process data page = page + 1 Do not assume an empty data array is the only end condition. Inspect the info object. 5.6 Pagination with page tokens The Get Records documentation supports page_token for more than 2,000 records. Important rules:

  • Use either page or page_token, not both.
  • The token is user-specific.
  • The token is bound to the original request parameters.
  • Keep the same filters and field selection when using the token.
  • The response can provide next_page_token.
  • The documented token validity is limited.
  • The documented maximum using token pagination is 100,000 records.
  • Each request still returns at most 200 records.

Example first request: GET /crm/v8/Contacts?fields=id,Last_Name,Email&per_page=200&page=1 Example next request: GET /crm/v8/Contacts?fields=id,Last_Name,Email&per_page=200&page_token={next_page_token} A token is not a bookmark that can be combined with a changed query. Changing fields, filters, sorting or other request parameters can produce TOKEN_BOUND_DATA_MISMATCH. 5.7 Pagination exercise A CRM account contains 430 Contacts. You request: per_page=200 Answer these questions:

  1. How many calls are needed without a page token?
  2. What page values are used?
  3. What field tells you whether another page exists?
  4. What should you store if the API returns a next_page_token?

Expected answer:

  1. Three calls.
  2. Pages 1, 2 and 3.
  3. info.more_records.
  4. The token, along with the original request parameters and the user context.
  5. Create, Update, Delete, Related Records and Attachments

6.1 Create a Contact The documented create endpoint is: POST {api-domain}/crm/v8/Contacts Required create scope pattern: ZohoCRM.modules.{module_name}.CREATE Request: { "data": [ { "Last_Name": "Rivera", "Email": "nova-api-test@example.com", "Phone": "+1-555-010-0142" } ], "trigger": [] } The trigger value of [] is shown here for a controlled test where workflow execution is intentionally skipped. A production operation must decide whether CRM automation should run. The documented insert API supports up to 100 records in one call. Multi-record responses preserve input order, which allows the caller to associate each response with its input record. A successful response may resemble: { "data": [ { "code": "SUCCESS", "details": { "id": "5725767000001234567", "Created_Time": "2026-10-06T10:30:00+00:00", "Modified_Time": "2026-10-06T10:30:00+00:00" }, "message": "record added", "status": "success" } ] } The timestamp and ID above are illustrative. They were not returned by a live call. 6.2 Duplicate behavior The insert documentation states that duplicate checks are performed for unique fields. A duplicate can return an error even when the JSON is valid. Nova’s preferred customer-resolution sequence is: search by stable customer match key → one result: use existing CRM ID → no result: create → multiple results: stop and send to review Do not retry a duplicate-data error as though it were a network timeout. 6.3 Update a specific Contact The documented endpoint is: PUT {api-domain}/crm/v8/Contacts/{record_id} Example: curl --request PUT \ --url "https://www.zohoapis.com/crm/v8/Contacts/5725767000001234567" \ --header "Authorization: Zoho-oauthtoken ${ACCESS_TOKEN}" \ --header "Content-Type: application/json" \ --data '{ "data": [ { "Phone": "+1-555-010-0199" } ], "trigger": [] }' The bulk update form is: PUT {api-domain}/crm/v8/Contacts Each record in the data array must include its id. The documented maximum for one update call is 100 records. 6.4 Conditional update The update documentation supports: If-Unmodified-Since: 2026-10-06T10:30:00+00:00 This protects against overwriting a record changed after the caller last read it. If CRM returns ALREADY_MODIFIED with HTTP 412:

  1. Do not blindly overwrite the record.
  2. Fetch the current record.
  3. Compare the intended change with the current value.
  4. Ask whether the incoming value still owns the field.
  5. Retry only after applying the conflict rule.

6.5 Delete a record The documented delete forms are: DELETE {api-domain}/crm/v8/Contacts/{record_id} or: DELETE {api-domain}/crm/v8/Contacts?ids={record_id1},{record_id2} Required scope pattern: ZohoCRM.modules.{module_name}.DELETE The documented maximum is 100 records per delete call. Example: curl --request DELETE \ --url "https://www.zohoapis.com/crm/v8/Contacts/5725767000001234567?wf_trigger=false" \ --header "Authorization: Zoho-oauthtoken ${ACCESS_TOKEN}" Deletion is destructive. In Nova, delete should normally be a controlled administrative operation, not part of routine request synchronization. 6.6 Related records The general related-records path is: GET {api-domain}/crm/v8/{module_api_name}/{record_id}/{related_list_api_name} Example: GET /crm/v8/Contacts/5725767000001234567/Notes?fields=id,Owner,Parent_Id Required scope pattern: ZohoCRM.modules.{module_API_name}.READ A related list request requires fields. The documented default and maximum per_page value is 200. Use the href from related-list metadata whenever possible: Contacts/{ENTITYID}/Notes Replace {ENTITYID} with the actual CRM record ID. 6.7 List attachments The documented attachment-list endpoint is: GET {api-domain}/crm/v8/{module_api_name}/{record_id}/Attachments Required scopes include: ZohoCRM.modules.{module_name}.READ ZohoCRM.modules.attachments.READ Example: curl --get \ --url "https://www.zohoapis.com/crm/v8/Contacts/5725767000001234567/Attachments" \ --data-urlencode "fields=id,Owner,File_Name,Created_Time,Size,Parent_Id" \ --header "Authorization: Zoho-oauthtoken ${ACCESS_TOKEN}" A response may include: { "data": [ { "id": "5725767000001234999", "File_Name": "inspection-photo.jpg", "Size": 183420, "Created_Time": "2026-10-06T11:00:00+00:00", "$se_module": "Contacts" } ], "info": { "count": 1, "page": 1, "per_page": 200, "more_records": false } } 6.8 Upload an attachment The documented upload endpoint uses: POST {api-domain}/crm/v8/{module_api_name}/{record_id}/Attachments The request is multipart form data and accepts either:

  • A file.
  • An attachment URL.

Do not send both in the same request. Example file upload: curl --request POST \ --url "https://www.zohoapis.com/crm/v8/Contacts/5725767000001234567/Attachments" \ --header "Authorization: Zoho-oauthtoken ${ACCESS_TOKEN}" \ --form "file=@./fixtures/inspection-photo.jpg" Attachment uploads require attachment create scope in addition to the module permissions. For the introductory collection in this chapter, attachment listing is automated and upload is a manual sandbox exercise. This prevents a test run from attaching an unintended file.

  1. Credits, Batch Size and Concurrency

7.1 API credits Zoho CRM calculates API usage using credits in a rolling 24-hour window. The official API Limits page states that:

  • Many API calls consume one credit.
  • Some operations consume more.
  • Insert, update and upsert consume one credit for every 10 records.
  • A maximum of 100 records can be inserted or updated in one call.
  • The maximum credit deduction for those calls is therefore 10 per call.
  • Metadata calls also consume credits.
  • Deluge CRM integration tasks consume the corresponding API credits.

Do not calculate an integration’s cost only from the number of HTTP calls. The endpoint and batch size matter. Example: 25 individual Contact creates: 25 calls and approximately 25 create credits

One create call containing 25 Contacts: 1 call and approximately 3 create credits The second option is more efficient, but it requires:

  • Record-level response handling.
  • Input-to-response correlation.
  • Partial-success recovery.
  • A decision about whether one invalid record should block the batch.

7.2 Concurrency Concurrency limits restrict how many requests can be active simultaneously for an organization and application. The official limits page documents edition-dependent organization/application concurrency limits and a sub-concurrency limit of 10 for selected expensive operations, including:

  • Get Records with cvid or sort_by.
  • Insert, update or upsert when the record count is greater than 10.
  • Search invoked from a function.
  • Query API.
  • Composite API.
  • Convert Lead.
  • Send Mail.

When the sub-concurrency limit is reached, the documented error is TOO_MANY_REQUESTS. 7.3 Design rules for Nova Use these rules in Creator:

  1. Do not launch one CRM request per row in an uncontrolled parallel loop.
  2. Batch only when the operation is idempotent and the response can be correlated.
  3. Limit concurrent workers in the integration function.
  4. Add jitter to retry delays.
  5. Stop retrying after a bounded attempt count.
  6. Record the last response classification.
  7. Reconcile uncertain writes by searching with the external key or other stable match key.
  8. Do not retry validation, permission or duplicate errors without changing the request or authorization.

7.5 Cost example A nightly reconciliation retrieves 430 Contacts with 200 records per page. Without a page token: 3 GET calls If each call consumes one credit: approximately 3 credits If the reconciliation also makes: 1 module metadata call 1 field metadata call 1 related-list metadata call 10 Contact updates The approximate call and credit model must be calculated from the actual endpoints and the current API Limits documentation. Metadata calls are not free, and repeated metadata discovery inside every request is wasteful.

  1. Error Interpretation and Recovery

8.1 Read the entire error A useful error record contains: correlation_key request_name method sanitized_url http_status response_code response_message response_details attempt_number elapsed_ms environment crm_module crm_record_id external_request_key Never log the access token or a full sensitive customer payload. A CRM response may contain: { "code": "INVALID_QUERY", "details": { "api_name": "Email", "value": "not-a-valid-query" }, "message": "invalid query formed", "status": "error" } The details object is often more useful than the top-level message. 8.2 Error classification table

8.3 Error decision tree flowchart TD A[CRM response] --> B{HTTP success?} B -->|No| C{Authentication or scope?} C -->|Yes| D[Repair token or scope] C -->|No| E{Permission?} E -->|Yes| F[Repair CRM access] E -->|No| G{Data, URL or duplicate?} G -->|Yes| H[Correct request; do not blind retry] G -->|No| I{Transient or limit?} I -->|Yes| J[Backoff and bounded retry] I -->|No| K[Escalate with correlation key] B -->|Yes| L{Every data item successful?} L -->|No| M[Process partial results and reconcile failures] L -->|Yes| N[Persist CRM ID and outcome] 8.4 Partial success A multi-record create or update can return HTTP 207 with individual result entries. Example: { "data": [ { "code": "SUCCESS", "details": { "id": "5725767000001234567" }, "message": "record added", "status": "success" }, { "code": "DUPLICATE_DATA", "details": { "api_name": "Email" }, "message": "duplicate data", "status": "error" } ] } The caller must not mark both input records as successful. Use input order and an input-side external key: input[0].external_request_key → data[0] input[1].external_request_key → data[1] 8.5 Unknown outcome after timeout A timeout is not proof that CRM rejected the operation. For a create:

  1. Keep the same external request key.
  2. Search for the intended unique customer data.
  3. If exactly one matching CRM record exists, store its ID.
  4. If no match exists, retry only if the request is safe.
  5. If multiple matches exist, stop for review.
  6. Write the final decision to Sync_Status.

11.1 Knowledge check Question 1 A user sees the field label Nova Customer Key, but the field metadata returns: { "display_label": "Nova Customer Key", "api_name": "External_Customer_Key__s" } Which value belongs in an API request? Question 2 A Get Records request returns: { "info": { "per_page": 200, "page": 10, "more_records": true, "next_page_token": "abc123" } } What should the caller do if it needs records after the first 2,000? Question 3 A create request times out. Should the integration immediately submit the same create request again? Question 4 A Search API call returns OAUTH_SCOPE_MISMATCH. Which additional scope is specifically associated with Search API secure search? Question 5 An update returns HTTP 412 with ALREADY_MODIFIED. What does this indicate? Question 6 A response returns HTTP 207 with one successful record and one DUPLICATE_DATA result. Should the caller mark the entire batch successful? Question 7 Why does the attachment-list request include a fields query parameter? Question 8 Which system owns Job_Status in the Nova baseline? 11.2 Answers Answer 1 Use: External_Customer_Key__s The API uses the field’s api_name, not its display label. Answer 2 Use the next_page_token with the original request parameters. Do not send page and page_token together. Answer 3 No. The outcome is unknown. First reconcile by searching for the intended customer using the same stable match key. A second create could produce a duplicate. Answer 4 ZohoSearch.securesearch.READ The module read scope is also required. Answer 5 The record was modified after the timestamp supplied in If-Unmodified-Since. Re-read the record and apply the conflict rule. Answer 6 No. Process each data entry independently and reconcile the failed record. Answer 7 The documented attachment-list endpoint requires fields to specify which attachment fields should be returned. Answer 8 Creator owns Job_Status. It is an operational workflow state, not CRM customer identity. 11.3 Chapter recap A dependable CRM REST integration follows this sequence: confirm API version and data centre → discover module API name → discover field API names and permissions → discover related-list hrefs → select narrow fields → resolve identity before writing → send documented request envelope → inspect HTTP and record-level results → classify failures → apply bounded retry or reconciliation → persist CRM ID, correlation key and sync outcome The most important principles are: 1. Use API names, not screen labels. 2. Keep the API domain configurable. 3. Verify the API version. 4. Declare scopes and user permissions. 5. Treat CRM IDs and Nova business IDs as different identifiers. 6. Search before creating a customer. 7. Do not retry an uncertain create without reconciliation. 8. Process partial-success responses record by record. 9. Respect credits and concurrency.

  1. Keep Creator’s operational states separate from CRM customer identity.
  2. Use metadata to protect the integration from label and layout changes.
  3. Do not claim that a request ran when it was only designed or mocked.
